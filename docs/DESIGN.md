# DESIGN — kaleido.chat 設計図

この文書が最上位の設計文書です。決定はすべてここに集約し、詳細は各専門文書へ委ねます。

**現在の状態: 設計のみ。コードは1行も書かれていません。**

---

## 0. 開発の原則

判断に迷ったとき、この順で優先します。

1. **動くこと** — 壊れている機能より、無い機能のほうがましである
2. **軽いこと** — コンセプトを裏切る変更はしない
3. **読めること** — 人間が最初に読んで理解できる名前と構造にする
4. **小さいこと** — 一つの箇所に一つの役割。必要以上の複雑さと重複を避ける

行数の削減より、安全性・読みやすさ・保守性を優先します。
最終的な設計・採用・変更の判断と責任は、常に人間が持ちます。

## 1. プロダクト定義

### コンセプト

> Discord風の見た目でMatrixを使う、**動作が軽い**クライアント。

### ターゲット

**Discord から Matrix へ移行するユーザー。**

Matrix の既存ユーザーを奪うのではなく、Discord に慣れた人が Matrix へ来たときに「操作を覚え直さなくていい」と感じられることを狙います。したがって画面構成と語彙は Discord に合わせます。

### 既存クライアントとの差別化

| # | 主張 | 実現手段 |
|---|---|---|
| 1 | 日本語対応 | 最初から日本語をベースに設計する。用語も日本語へ変換する（[UX_SPEC](UX_SPEC.md)） |
| 2 | バグが無い | v0.1 のスコープを極端に絞る。VC を外す。テスト→再ビルドを回す |
| 3 | 安定性と機動性は Sable 相当 | 機能一覧を [FEATURE_REFERENCE](FEATURE_REFERENCE.md) で棚卸しし、必要なものだけ実装する |
| 4 | 非Electron | Web (PWA)。Electron を使わない |
| 5 | Rust製 | Leptos + matrix-rust-sdk。UI からストレージまで Rust |

> **注意：「バグが無い」は主張として危うい。** 新規実装であり、依存する matrix-rust-sdk の WASM 対応も枯れていません。この主張を守る唯一の方法は**スコープを絞ること**です。機能を足すたびにこの主張は弱くなります。

### v0.1 スコープ

- ログイン（パスワード ＋ OIDC の両対応）
- トーク一覧の表示（Sliding Sync）
- テキストメッセージの送受信
- 送信中 / 送信失敗の表示
- 暗号化ルームの復号表示
- オフライン表示と再接続
- ログアウト

### v0.1 でやらないこと（未承認・要レビュー）

実装しないだけでなく、**UIにも出さない**もの:

- 画像・動画・音声・ファイルの送受信
- 返信、リアクション、編集、削除
- スレッド
- 新規ルーム作成、招待
- 検索
- 通知（プッシュ・デスクトップ通知とも）
- 複数アカウント
- 新規登録（サインアップ）
- ユーザープロフィール編集
- 高度なルーム設定・権限管理
- 鍵バックアップ、デバイス検証（cross-signing）
- カスタムテーマ、ライトモード

**UIには出すが機能しないもの:**

- ボイスチャンネル（🔊 表示のみ。詳細は [VC_SPEC](VC_SPEC.md)）

## 2. 「軽い」の定義

主観で終わらせないため、数値目標と測定方法をセットで定義します。詳細は [PERFORMANCE_BUDGET](PERFORMANCE_BUDGET.md)。

**主軸は起動速度とメモリ。** 初回ダウンロード量も測りますが、優先度は下です（Leptos + matrix-rust-sdk を WASM で動かす以上、転送量で JavaScript 実装に勝つのは難しいため）。

**具体的な数値は Spike 0 の実測後に確定します。** 実測前に決めた数字には根拠がないため、いまは測定項目と測定方法だけを定義しています。

## 3. 技術スタック

| 項目 | 決定 | 備考 |
|---|---|---|
| 配布形態 | **Web (PWA) のみ** | Tauri は一切使わない |
| UI フレームワーク | Leptos | |
| 状態管理 | signal | Leptos 標準 |
| ビルド | trunk（CSR のみ） | SSR は使わない |
| CSS | Tailwind CSS | Trunk の `[[hooks]]` で Tailwind CLI を build 段階に噛ませる |
| Matrix SDK | matrix-rust-sdk（`wasm32-unknown-unknown`） | |
| ストレージ | **IndexedDB のみ** | `matrix-sdk-indexeddb`。SQLite・OSキーチェーンは対象外 |
| ホスティング | 静的ホスティング | 将来 `kaleido.chat` ドメインでの配信を想定 |

### Tauri を使わない理由

デスクトップ版は「ネイティブ実行 ＋ SQLite ＋ OSキーチェーン」で確かに速く安全になりますが、Web版と実装が二重化し、工数がほぼ倍になります。無料の静的ホスティングで世界中へ届けることを優先し、**Web (PWA) に振り切りました**。

**代償**：ネイティブ実行という退路が無くなりました。matrix-rust-sdk が WASM で動かなければ、この路線は成立しません（§7 参照）。

## 4. Matrix 2.0 への対応

| 柱 | 対応 |
|---|---|
| **Sliding Sync**（MSC4186） | **採用。** 起動速度の最大のレバー。接続先を matrix.org に固定するため、Synapse の既定有効に乗れる |
| **Next-gen Auth（OIDC）** | **採用。** 従来のパスワードログインと両対応する |
| **Native Group VoIP（MatrixRTC）** | **v0.2。** v0.1 は外部リンクで回避（[VC_SPEC](VC_SPEC.md)） |
| **E2EE** | 下記 |

### 接続先ホームサーバー

**matrix.org 固定。** ユーザーにサーバー選択を見せません。移行組にとって「サーバーを選ぶ」は最初の脱落ポイントになるためです。

将来的に自前運用や任意サーバー指定を足す余地は残しますが、v0.1 では設定項目にしません。

### E2EE の方針

Matrix ではルームの暗号化は**一度ONにするとOFFに戻せません**。また **matrix.org のDMは既定で暗号化されます**。したがって:

- **復号は常に対応する。** 対応しなければDMが読めず、クライアントとして成立しません。E2EE対応は選択制にできません
- **ユーザーが選べるのは「自分が作る新規ルームを暗号化するか」だけ** です
- 鍵とセッションは IndexedDB へ保存します。鍵の生成・保護は Web Crypto API などブラウザネイティブの機能へ委ね、**独自の暗号実装は行いません**

> **Web版の保護レベルの限界（正直に書く）**
> IndexedDB は OSキーチェーン相当の保護を提供しません。同一オリジンで動く他のスクリプトや、端末を物理的に触れる第三者に対して、ネイティブアプリほど強くありません。
> この限界は README とアプリ内のどこかでユーザーへ明示します。**「ネイティブ版より安全」と主張しません。**

## 5. 画面構成とUI

### 4ペイン構成

```text
┌────┬──────────┬─────────────────────────┬──────────┐
│ ①  │    ②     │           ③             │    ④     │
│スペ│ チャンネル │        タイムライン        │ メンバー  │
│ース│   一覧    │                         │   一覧    │
│バー│          │                         │          │
└────┴──────────┴─────────────────────────┴──────────┘
```

### Matrix 概念 → Discord 語彙のマッピング

**この対応表が設計の核です。** 内部コードでは Matrix 用語を使いますが、UIには出しません。

| Matrix | UI表示 |
|---|---|
| Space | サーバー |
| サブスペース | カテゴリー |
| Room | チャンネル |
| Homeserver | 接続先 |
| User ID | あなたのID |
| Event | メッセージ |
| Device | 使用中の端末 |
| Sync | 更新 |
| Encrypted Room | 保護されたチャンネル |

### レスポンシブ方針

| 画面幅 | Tailwind | 表示ペイン |
|---|---|---|
| `< 768px` | (base) | **1ペイン**（③のみ。①②は左ドロワー、④は右ドロワー） |
| `>= 768px` | `md:` | **2ペイン**（①②合体サイドバー ＋ ③） |
| `>= 1024px` | `lg:` | **3ペイン**（① ＋ ② ＋ ③） |
| `>= 1280px` | `xl:` | **4ペイン**（① ＋ ② ＋ ③ ＋ ④） |

スマホでは左右のドロワーが③に覆いかぶさり、背景に半透明のバックドロップを敷きます。バックドロップのタップで閉じます。

**スクロールの独立性**：各ペインは個別に `overflow-y-auto` を持ち、`body` は `overflow-hidden` で固定します。ページ全体がスクロールすると「Webサイト感」が出てアプリらしさが失われるためです。

### デザイン言語

**レイアウト構造は Discord、見た目の質感は [Commet](https://github.com/commetchat/commet) に寄せます。**

- **構造**（4ペイン、情報密度、ホバー挙動、語彙）→ Discord
- **質感**（クリーンで簡素、ツールらしい佇まい）→ Commet

Commet は Discord風UIを持つ Matrix クライアントで、「機能は豊富だがインターフェースは簡素」を掲げています。kaleido.chat が目指す方向と一致します。

具体的にはダークオンリー、独自の `midnight` パレット、スクエア基調の角丸、等幅フォント。詳細と全トークンは [DESIGN_LANGUAGE](DESIGN_LANGUAGE.md)。

> **Discord のブランド資産は使いません。** 配色・フォント・ロゴは独自のものを使います。商標およびトレードドレスの問題を避けるためです。
>
> **Commet のコードも使いません。** Commet は AGPL-3.0 かつ Flutter 製です。ライセンス上コピーできず、技術的にも Leptos へ持ち込めません。参照するのは**見た目の方向性だけ**です。

## 6. アーキテクチャ

### レイヤ分離

```text
┌─────────────────────────────────────────┐
│ UI層          Leptos コンポーネント        │  画面表示とユーザー操作のみ
├─────────────────────────────────────────┤
│ 状態管理層     signal                     │  選択中チャンネル、メッセージ一覧、
│                                          │  ログイン状態、エラー状態
├─────────────────────────────────────────┤
│ core層        データ型・変換・共通ロジック   │  環境非依存
├─────────────────────────────────────────┤
│ SDKラッパ層    matrix-rust-sdk            │  Matrixサーバーとの通信
├─────────────────────────────────────────┤
│ ストレージ層   IndexedDB                   │  セッション・設定・キャッシュ
└─────────────────────────────────────────┘
```

### 禁止事項

- **UI層から matrix-rust-sdk を直接呼ばない**
- **UI層から IndexedDB を直接触らない**
- **core層にブラウザ固有処理を入れない**

core層をブラウザ非依存に保つのは、将来デスクトップ版を出す可能性への保険です。v0.1 ではその境界を維持するだけで、実際の差し替え機構は作りません。

### 性能に効く処理はすべて Rust 側に置く

**通信・同期・メモリ管理・暗号化・キャッシュは、UI層ではなく core層 / SDKラッパ層で行います。**

- 同期は Sliding Sync で core層が一元管理する。UIのライフサイクルで止めない
- タイムラインのメモリはRust側で持ち、UIへは表示に必要な範囲だけ渡す
- 大量のメッセージをUI層のシグナルへ丸ごと持たせない
- JavaScript 側に状態を持たない。JS interop は必要最小限にとどめる

「軽い」を実現する処理はすべてRustにあり、UI層は薄い表示層である、という状態を保ちます。

### モジュール構成

初期構成は次の3領域に限定します。過剰な分割はしません。

```text
src/
├── ui/          Leptos コンポーネントと画面
├── core/        共通データ型、入力規則、エラー分類
└── matrix/      matrix-rust-sdk ラッパ、同期、IndexedDB
```

公開API・データモデル・エラー型の定義は [CORE_SPEC](CORE_SPEC.md)。

### エラーハンドリング方針

- 生のSDKエラーをUIへ直接渡さない
- 文字列だけのエラーにしない
- アプリ共通のエラー分類へ変換する
- 利用者には短い日本語メッセージを表示する
- 詳細原因はログへ記録する
- パスワードやアクセストークンはログへ出さない
- 回復可能なエラーではアプリを終了させない
- 本番処理で `unwrap()` / `expect()` を原則使用しない

エラー分類と日本語文言の対応表は [CORE_SPEC](CORE_SPEC.md) と [UX_SPEC](UX_SPEC.md)。

### オフライン / 再接続戦略（未承認・要レビュー）

開発者が回線の不安定な環境で作業しているため、**切断は例外ではなく通常状態**として設計します。

- 切断時：画面上部に控えめなバーを出す（モーダルは使わない）。「インターネットに接続されていません。再接続を待っています。」
- 再接続時：「接続が戻りました。」を数秒だけ表示して消す
- 再接続は指数バックオフ（初回1秒 → 最大30秒程度）で自動リトライする。ユーザー操作を要求しない
- 切断中も**既に読み込んだメッセージは読める**（IndexedDBのキャッシュから表示）
- 切断中の送信は失敗として表示し、`transaction_id` を保持する。自動再送は v0.1 では行わず、手動の「再送」ボタンのみ
- 同期の二重起動を防ぐ（[CORE_SPEC](CORE_SPEC.md)）

## 8. Spike 0 — 実装前の必須検証

**このプロジェクトで最初にやることは、機能の実装ではなく技術的な生存確認です。**

使い捨てのコードで、以下がブラウザ上で通るかを確認します。

1. `wasm32-unknown-unknown` でビルドした matrix-rust-sdk で **パスワードログイン**
2. **Sliding Sync** でルーム一覧の取得
3. **暗号化ルームの復号**
4. **IndexedDB** へのセッションと鍵の永続化
5. あわせて **WASMバンドルサイズ・起動時間・アイドル時メモリ**を実測

### 合否の扱い

- **合格** → 実測値を [PERFORMANCE_BUDGET](PERFORMANCE_BUDGET.md) へ書き込み、v0.1 の実装に入る
- **不合格** → **Leptos を諦め、React + matrix-js-sdk へ路線変更する**

退路を選んだ場合、差別化の「Rust製」は失いますが、製品は出せます。matrix-js-sdk は Element / Cinny / Sable が実戦投入しており、暗号化も matrix-rust-sdk の crypto crate を WASM 化したもの（`@matrix-org/matrix-sdk-crypto-wasm`）が担当するため、「暗号化は Rust」は維持できます。

**この判断を先送りしません。** Spike 0 の前に UI を作り込むと、路線変更時に捨てる量が増えます。
