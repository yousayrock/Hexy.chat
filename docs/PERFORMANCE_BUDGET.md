# PERFORMANCE BUDGET

Hexy.chat のコンセプトは「動作が軽い」です。主観で終わらせないため、**測定項目・測定方法・目標値**を定義します。

> **目標値は未確定です。** Spike 0 の実測後に埋めます。
> 実測前に決めた数字には根拠がないため、いまは「何をどう測るか」だけを定義しています。

---

## 優先順位

1. **起動速度** — 開いてからメッセージが読めるまで
2. **メモリ** — 常駐させても軽いこと
3. **操作の応答性** — チャンネル切替、スクロール
4. **初回ダウンロード量** — 優先度は最下位

### なぜ初回ダウンロード量が最下位なのか

Leptos + matrix-rust-sdk を WASM で動かす以上、転送量で JavaScript 実装に勝つのは困難です。SDK 全体が WASM バンドルに載るためです。

**軽さの勝負どころは転送量ではなく、起動後の実行性能とメモリ**です。Electron 系クライアントが 400〜700MB を消費するのに対し、ブラウザ上の WASM アプリはそこで明確に勝てます。

ただし転送量を無視はしません。測定して記録し、極端に膨らんだら手を打ちます。

## 測定項目

| # | 項目 | 測定方法 | 目標値 |
|---|---|---|---|
| 1 | 起動〜トーク一覧表示（キャッシュあり） | 2回目以降のリロードで、DevTools Performance の navigationStart からチャンネル一覧の初回描画まで | **未定**（Spike 0 後） |
| 2 | 起動〜トーク一覧表示（初回） | キャッシュを空にした状態で同上 | **未定** |
| 3 | チャンネル切替 | クリックからタイムライン描画完了まで | **未定** |
| 4 | アイドル時メモリ | 起動して5分放置後、Chrome タスクマネージャのメモリフットプリント | **未定** |
| 5 | 長いタイムラインのスクロール | 1000件表示状態でスクロールし、DevTools Performance でフレームレートを記録 | **未定** |
| 6 | 初回転送量 | DevTools Network で、キャッシュ空の状態の総転送量（gzip/brotli 後） | **未定** |
| 7 | WASMバンドル単体のサイズ | ビルド成果物の `.wasm` を brotli 圧縮したサイズ | **未定** |

## 測定条件を固定する

数字が比較可能であるために、以下を固定します。

- **ブラウザ**：Chrome 安定版（バージョンを記録する）
- **アカウント**：測定用の matrix.org アカウント。**参加ルーム数を記録する**（Sliding Sync の効果はルーム数に強く依存するため）
- **回線**：DevTools のネットワークスロットリングは使わず、実回線で測る。回線種別を記録する
- **端末**：測定に使った端末のCPU・メモリを記録する

**測定するたびに、上記の条件と日付を結果に併記します。** 条件の違う数字を並べても意味がありません。

---

## 比較対象

「軽い」を主張する以上、比較対象が必要です。同じ条件で以下も測ります。

| 対象 | 種別 | 備考 |
|---|---|---|
| Element Web | Web | Matrix の標準的なクライアント |
| Cinny | Web | 軽量を謳う Web クライアント |
| Discord（ブラウザ版） | Web | ターゲットユーザーの移行元 |
| Discord（デスクトップ版） | Electron | 「非Electron」の主張の対照 |

**Hexy.chat がこれらに負けている項目があれば、そのまま記録して公開します。** 都合の悪い数字を隠すと、差別化の主張そのものが信用を失います。

---

## CI での扱い

Spike 0 で目標値が決まったら、以下を CI に組み込みます。

- **WASMバンドルサイズの上限チェック** — 閾値を超えたらビルドを落とす
- サイズの推移を記録し、増加の原因が追える状態にする

起動速度とメモリは環境差が大きく CI での自動判定に向かないため、**リリース前の手動測定**とします。
